# 架构解析 (Architecture)

Agent-Bridge 的架构设计哲学极度崇尚“隔离”与“不信任”。在 Multi-Agent 系统中，单体 Agent 往往容易陷入幻觉或由于上下文污染导致错误修改。为了解决这个问题，我们将系统强制切分为**三个完全物理隔离的节点**。

## 1. 三权分立模型

### 1.1 Builder (施工方)
- **定位**：代码与资产的生产者。
- **运行环境**：通常是一个拥有完整文件读写与终端执行权限的 LLM IDE（如 Cursor, Workbuddy 等）。
- **心智模型**：
  - “我只关心当前的 Task。”
  - “写完代码，跑通本地测试，提交代码，我就立刻挂起休息，绝不多管闲事。”
- **无权**：无法自己修改状态机进入下一阶段，必须等待审查。

### 1.2 Supervisor (监工方)
- **定位**：冷酷的代码审查者。
- **运行环境**：通常是一个挂在后台的自动化 Agent（如 Antigravity IDE），拥有完整的 Lint/Test 执行环境。
- **心智模型**：
  - “我不写业务代码，我只跑测试和审查差异。”
  - “只要发现一丁点警告、Lint 报错或与 PRD 不符，我就会生成刻薄的 `verdict.json` 强行打回。”
- **无权**：不直接修改业务代码（为了防止自己陷入写 Bug 的循环）。

### 1.3 Watchdog (看门狗)
- **定位**：无情的流水线传送带。
- **运行环境**：纯原生 Node.js 后台进程。
- **心智模型**：
  - “我不懂什么是代码，也不懂什么是大模型。”
  - “我只看 `bridge.md` 里的 `status` 字段。如果变了，我就去踹醒该干活的 Agent。”
- **无权**：没有任何业务逻辑决策能力。

## 2. 基于文件锁的互斥 (Mutex via File System)

传统 Agent 框架通常通过 RPC / WebSocket / Memory 进行进程间通信（IPC）。但在实际工程中，跨平台跨 IDE 建立 WebSocket 非常困难且不稳定。

Agent-Bridge 选用了最古老但也最可靠的通信方式：**本地文件系统锁定（File Lock）**。

所有的状态流转（详见 [协议规范](protocol_spec.md)），都必须通过原子化修改根目录下的 `.bridge/` 锁文件或 `bridge.md` 状态机文件来实现。这保证了在同一时刻，无论有多少个大模型在运行，都**只有唯一一个 Agent 拥有对代码库的修改权**，从根本上消灭了并发覆盖问题。
