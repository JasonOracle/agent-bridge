# Agent-Bridge 产品白皮书与架构文档

## 1. 产品定位 (Product Positioning)

**Agent-Bridge** 是一个极简的、基于纯文件状态机的多智能体（Multi-Agent）自动化协作桥接框架。

在当下大模型开发中，单体 Agent 往往受限于上下文窗口与执行连贯性，难以独自完成大型工程。而现存的 Multi-Agent 框架（如 AutoGen、MetaGPT）往往重度依赖特定的 Python 环境、庞大的第三方库，且极难跨平台（跨越不同的桌面客户端或不同的 IDE）进行协作。

Agent-Bridge 的核心使命，是提供一个**零依赖（Zero-dependency）、工具无关（Tool-agnostic）**的轻量级底层协议层，将任意两个隔离运行的 AI 编程助手，强行组合为一套具备“施工 - 审查 - 反馈”闭环的自动化流水线，实现真正的**长周期、零干预无人值守开发**。

## 2. 核心痛点解决 (Problem Solved)

*   **跨 IDE / 跨平台壁垒**：无论使用 Cursor、Workbuddy 还是 Antigravity IDE，只要该 Agent 具备读写本地文件与执行命令行的能力，即可直接接入。
*   **状态迷失与幻觉死循环**：单体 Agent 连续执行时极易产生幻觉和死循环。通过引入绝对的“三权分立”与“状态机强制锁”，从物理和逻辑层面切断错误的发散。
*   **环境依赖地狱**：完全由纯原生 Node.js 实现，没有任何 npm 三方包依赖，即插即用，极度轻量。

## 3. 核心架构：三权分立 (Core Architecture)

Agent-Bridge 的运行时架构由三个完全独立运行的节点构成：

### 3.1 施工方 (Builder)
*   **职责**：纯粹的代码生产者。负责读取需求任务，在工作区编写业务代码、运行本地测试代码，并进行 Git Commit 提交。
*   **特性**：处于极度专注模式，不关心全局进度。完成后强制自我挂起（通过调用阻塞脚本），交出控制流。

### 3.2 监工方 (Supervisor)
*   **职责**：纯粹的代码审查者。负责静态分析、架构审查、运行构建流水线、对比 PRD 边界。
*   **特性**：拥有绝对的“否决权”。如果代码不符合规范或跑不通构建，有权将状态打回并生成详细的 Review 报告，强制 Builder 重写。它不直接修改业务代码。

### 3.3 看门狗 (Watchdog)
*   **职责**：系统的节拍器与总枢纽。它不具备任何业务认知，仅通过轮询本地锁定文件（`.bridge` / `bridge.md`）中的状态标志位来驱动状态机。
*   **特性**：负责组装上下文、唤醒对应的 Agent，确保在任意时刻，只有单一 Agent 拥有读写权，彻底杜绝代码并发修改造成的脏数据覆盖。

## 4. 严谨状态机协议 (State Machine Protocol)

通过根目录文件作为信使，执行七态严格流转：

1.  **`PENDING_DEV`**: 等待施工方介入开发。
2.  **`IN_DEV`**: 施工方正在锁定工作区编写代码。
3.  **`PENDING_REVIEW`**: 施工方提交完毕，等待监工方审查。
4.  **`IN_REVIEW`**: 监工方正在锁定工作区进行审查。
5.  **`REJECTED`**: 审查未通过，附带失败报告，强制打回至 `PENDING_DEV`。
6.  **`APPROVED`**: 审查完美通过，推入下一个业务节点的 `PENDING_DEV`。
7.  **`COMPLETED`**: 全局任务达成，全员自动结束运行。

## 5. 典型应用场景 (Use Cases)

*   **隔夜重构 (Overnight Refactoring)**：下发一份 500 行的架构重构文档。关掉显示器，由 Builder 和 Supervisor 自行在深夜进行多轮对抗、试错与修复。
*   **严格合规交付**：利用强权 Supervisor，强制校验代码是否符合企业级 ESLint 规范、是否 100% 具备 TypeScript 类型约束，任何瑕疵将被无限次打回直至完美。
